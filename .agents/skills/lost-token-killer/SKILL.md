# Lost Token Killer

トークンの「ロスト（無駄消費）」を潰すための運用ルール。狙いは出力を雑にすることではなく、
**同じ情報に二度払わないこと**。品質に効いていない支出だけを削る。

ロストは5種類に分類できる。どれも「モデルが賢くないから起きる」のではなく、
**作業の順序が悪いから起きる**。順序を直せば品質は落ちない。

## 発動

発動したら冒頭に一行だけ宣言し、以降その旨を繰り返さない。

```
LTKモードON（結論ファースト・差分編集・一行報告で進めます）
```

## 1. 再読ロスト

同じ内容に二度払わない。ファイル全体の読み込みは、対象の構造を把握する初回だけ価値がある。
二度目以降に得られる新情報は編集した差分だけなので、そこだけ読む。

- `rg -n <pattern> <path>` で行位置を特定してから `sed -n '120,160p' <file>` で必要な範囲を読む
- 全文の再読は最終レビュー時と、他プロセスによる編集競合が疑われるときだけ
- 一度読んだ内容は要約をテキストで持ち回る。特に画像とスクリーンショットは再確認しない
  （画像トークンは重く、二度目に得られる情報はほぼゼロ）
- コンテキストが逼迫してきたら自分から `/compact` を促す。上限に当たってからの自動圧縮より安い

## 2. 再生成ロスト

既存ファイルの全文出力は、変えていない行にもう一度払う行為。差分だけ出す。

- 修正は `apply_patch` の差分ブロック（`@@` と `-` / `+`）で行う
- `*** Add File` は本当に新規のときだけ。既存パスへの全文上書きはしない
- 「全面的に作り直して」と明示されたときだけ再生成する
- 複数箇所の修正は1回の `apply_patch` にまとめる。往復そのものが固定コスト
- 検証スクリプトは初回に1本書いて使い回す。毎回書き直さない

## 3. 冗長出力ロスト

出力トークンにも金がかかる。読み手が意思決定に使わない行は削る。

- 返答は結論ファースト、3〜6文。変更内容の全文引用はせず、何をどう変えたかだけ書く
- コードをチャット本文に貼らない。ファイルに書いてパスを示す
- 検証結果は「OK / NG + 一行理由」
- 装飾・表・絵文字は最小限。箇条書きは要点のみ
- 提案やレビューも同じ。選択肢は最大3つ、各1〜2行。網羅より推奨を出す

## 4. 無駄往復ロスト

1往復には固定コストがある。答えが予測できる質問は、往復を1回買う価値がない。

- 「追記しますか？」と聞かない。必要と判断したら実行し、結果を一行報告する
- 曖昧な指示はリポジトリの既存文脈から補完して進め、置いた仮定は報告に一行添える
- 返答末尾に「他に直す点があればまとめてどうぞ」を添え、細切れ指示を先回りで防ぐ
- 存在確認は1コマンドで済ませる（`ls` → 判定 → 報告を1ターンで）

ただしこれは**可逆な操作に限る**。取り消せない操作は、往復1回より事故のほうが高い。
公開、削除、URL移行、権限変更、課金操作、本番マージは必ず事前確認する。
リポジトリの `AGENTS.md` に承認ルールがある場合は、そちらが常に優先する。

## 5. 過剰思考ロスト

推論の深さは難易度に合わせる。答えが一意に決まる作業に深い思考を足しても品質は上がらない。

- 定型作業（差分修正、ファイル移動、一行報告、既定フォーマットへの整形）は即実行する
- 設計判断とトレードオフ検討は初回の1回に集中させ、以降は決定に従って機械的に実行する
- 一度決めた方針（構造・命名・技術選定）は決定事項として扱う。再検討はユーザーが
  変更を指示したときだけ
- 可逆な操作は、考え込むより実行して結果で判断するほうが安い

Codex では推論エフォートを設定で直接変えられる。定型作業が続く見込みなら、
`/model` から低エフォートに落とすか、`~/.codex/config.toml` の
`model_reasoning_effort` を下げることを一度だけ提案する。

## セッション運用

- 修正が細切れに来そうなときはバッチ指示を促す
- 中間修正では対象箇所のスモークチェックのみ。フル検証はサインオフ直前に1回
- スクリーンショット検証は要求されたときだけ。既定はログとファイル内容で検証する
- 大きな構想はまず計画 Markdown を1ファイルに固め、実装ターンでは対象セクションだけ読む
- 繰り返し使う運用ルールは会話で毎回説明せず、`AGENTS.md` かこのスキルに固定する

## 出力フォーマット

```
修正完了: <変更点を1行>
変更箇所: <ファイル名> L120付近（○○を△△に）
未検証: <あれば1行、なければ省略>
```

複数件をまとめた場合:

```
3件修正完了: <要約1行>
1. <1行>
2. <1行>
3. <1行>
```

## 適用しない場面

節約が目的化すると本末転倒になる。次の場合は通常モードで進める。

- 初回の設計提案や要件定義など、思考の幅そのものが成果物である場面
- ユーザーが「詳しく説明して」と明示した場合
- 安全性・正確性の確認（削除、上書き、公開、課金）。ここは節約より正確さが優先
